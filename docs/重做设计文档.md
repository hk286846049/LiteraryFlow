# 0. 给 AI Agent 的最高优先级指令

本项目不是对旧项目进行局部修补。

**禁止沿用旧项目的 UI、Service、全局变量、执行逻辑、数据库结构和 OCR 轮询方式。**

新项目必须按照本文件从零建立核心架构。

优先级：

1. **能稳定运行**
2. **低功耗**
3. **OCR 感知可靠**
4. **任务可取消**
5. **状态可恢复**
6. **代码结构清晰**
7. **UI 完整**
8. **高级功能**

如果时间不足：

> 删除低优先级功能，不得破坏执行引擎、OCR、取消机制、数据库和任务闭环。

核心闭环必须优先完成：

```text
选择 App
→ 新建任务
→ 添加动作
→ 保存
→ 获取屏幕
→ OCR / 页面判断
→ 执行动作
→ 下一步
→ 完成 / 失败
→ 保存运行记录
```

# 1. 产品定位

LiteraryFlow 是一个**本地运行、个人使用的 Android 自动化工具**。

主要用途：

* 手游每日任务
* 手游签到
* 手游领取奖励
* 广告 App 自动操作
* 自动关闭广告
* 自动点击“领取/继续/跳过/关闭”
* 根据 OCR 判断当前页面
* 根据页面状态决定下一步动作
* 定时运行任务
* 循环运行任务

原项目已经具备任务配置、无障碍、OCR、截图、悬浮窗、调度等基础能力，但重做版本不得继承原实现方式。

# 2. 核心设计原则

## 2.1 OCR 是核心感知能力

本项目不是：

```text
Accessibility 优先
OCR 兜底
```

而是：

```text
                Perception
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
 Accessibility    OCR       Template/Image
       │            │            │
       └────────────┴────────────┘
                    ↓
              Screen State
                    ↓
                 Decision
                    ↓
                 Action
```

对于手游：

> OCR / 图像感知是主要页面判断手段。

对于广告 App：

> Accessibility 可以辅助，但不得假设广告页面存在可靠节点。

---

# 2.2 感知和执行彻底分离

必须区分：

```text
Perception
```

和：

```text
Action
```

OCR 的职责：

```text
“屏幕上有什么？”
```

Action Executor 的职责：

```text
“怎么点击？”
```

因此：

```text
OCR
→ text + bbox
→ Decision
→ Tap(x,y)
→ Accessibility / Shizuku 执行
```

不得让 OCR 模块直接调用 Accessibility 或 Shizuku。

---

# 2.3 Scheduler 和 Executor 分离

Scheduler：

> 决定什么时候运行。

Executor：

> 决定怎么运行。

原需求对此已有明确要求。

禁止：

```text
AlarmService
→ 直接执行任务
```

必须：

```text
Scheduler
→ StartTask(taskId)
→ ExecutionEngine
```

---

# 2.4 禁止高频轮询

禁止：

```kotlin
while (running) {
    screenshot()
    OCR()
    sleep(500)
}
```

必须采用：

```text
事件 / 页面变化
      ↓
是否需要感知？
      ↓
需要
      ↓
截图
      ↓
OCR
      ↓
缓存
```

---

# 2.5 不追求“万能自动化”

这是个人工具。

允许针对特定 App 做 Profile。

例如：

```text
Game A:
OCR + Shizuku + ROI

Game B:
OCR + Accessibility

Ad App C:
OCR + Template + Shizuku
```

# 11. 坐标系统

所有内部坐标必须统一为：

```text

```

```text

```

```text

```


```text

```

# 15. Adaptive OCR Scheduler

不要固定 2Hz。

实现：

```kotlin
enum class PerceptionMode {
    IDLE,
```

---

## IDLE

条件：

* 当前动作不需要视觉
* 页面没有变化
* 等待任务结束
* 任务暂停

行为：

```text
不截图
不 OCR
```

---

## NORMAL

普通页面判断。

建议：

```text
500ms ~ 1500ms
```

但具体频率由状态决定。

---

## FAST

页面刚进入、广告刚出现、正在寻找目标。

可以短时间提高频率。

例如：

```text
200ms
400ms
800ms
1200ms
```

一旦页面稳定，自动降频。

# 21. OCR 图像降采样

不要硬编码：

```text
所有图片 → 720p
```

使用：

```text
AdaptiveResolutionPolicy
```

根据：

* 当前 ROI
* 文字尺寸
* 当前设备
* OCR 模式

决定尺寸。

基本策略：

```text
全屏首次 OCR：
最大边 1080

小 ROI：
保持足够文字高度
必要时放大 1.5~2x

大字体：
允许 720
```

目标是降低计算量，而不是追求固定分辨率。

# 109. 最终原则

整个项目只记住下面这 12 条：

```text
1. OCR 是核心感知，不是备用方案。
2. OCR 不等于持续 OCR。
3. 页面变化才触发重新感知。
4. ROI 优先于全屏 OCR。
5. OCR 结果必须缓存。
6. ScreenState 必须独立。
7. Perception 和 Action 必须分离。
8. Accessibility 和 Shizuku 都只是 Action Channel。
9. Scheduler 和 Executor 必须分离。
10. Task 配置和 Run 状态必须分离。
11. 所有长任务都必须可取消、可超时。
12. 没有必要做的功能，一律不要在 MVP 加。
```

# 113. 最终产品形态

最终不是一个：

> “不断截图、不断 OCR、不断点击”的脚本。

而是：

```text
             Task
              ↓
          State Machine
              ↓
        ┌─────┴─────┐
        ↓           ↓
   Perception     Action
        ↓           ↓
      OCR       Shizuku /
      Cache     Accessibility
        ↓           ↓
     ScreenState ← Decision
              ↓
            Next
```

核心思想：

> **感知一次，缓存结果；变化才重新感知；确定目标后再执行；执行完成立即释放资源。**

这样才同时适合**手游动态 Canvas/OpenGL 页面**和**布局高度动态的广告 App**，又能把原项目最大的“Bug 多 + 特别费电”问题从架构层解决，而不是继续在旧实现上打补丁。
